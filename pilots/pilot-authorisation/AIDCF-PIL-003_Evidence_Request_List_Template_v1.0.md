# 1. Purpose

AIDCF-009 B6 requires claim-specific evidence requests that record evidence class, period, operating state, quality floor and sufficiency floor (WP-06). For the mini-pilot these requests are not drafted by hand: they are derived deterministically from the Starter Profile (AIDCF-PIL-001 §6) and the registry evidence profiles, so that any two teams using the same registry version issue the same list. This makes evidence availability (PM-03, PM-04) comparable across pilots.

The CSV is the request list. This document explains how it is built, what each column means, and how to issue and track it.

# 2. Derivation rule

For each of the 58 Starter Profile controls, with registry profile claim type p and mandatory claim types at AL3 given by L = min(AL3, r) (AIDCF-010 Part IV):

| **Row type (`requestBasis`)** | **When** | **Content** | **`al3Use`** |
|---|---|---|---|
| `PROFILE_MANDATORY_ITEM` | The mandatory claim type equals p (p is DESIGN or IMPLEMENTATION). | One row per registry `mandatoryItems` entry, with the profile's required and optional classes, quality floor, sufficiency floor, state coverage, period, independence, acceptable alternatives and unknownEffect carried unchanged. | `MANDATORY` |
| `CLAIM_TYPE_PATTERN` | The mandatory claim type is shallower than p (DESIGN of any control with p deeper than DESIGN; IMPLEMENTATION of any control with p deeper than IMPLEMENTATION). | One row stating the AIDCF-008 §29 minimum pattern for that claim type (DESIGN: E1 design evidence with competent technical analysis; IMPLEMENTATION: E2 configuration or as-built evidence with E3 or E6 corroboration, reconciled to the approved design). The profile quality floor and state coverage are carried; sufficiency target S3 (AIDCF-PIL-001 §6.5). | `MANDATORY` |
| `PROFILE_ITEM_ABOVE_AL3` | p is OPERATION, EFFECTIVENESS or RESILIENCE. | One row per registry `mandatoryItems` entry. The pilot asks only whether the item exists, its date and where it is held; it does not assess it for p. | `AVAILABILITY_ONLY` |

For each criterion of each in-scope gate (CG-01, CG-02, CG-03, CG-05, CG-06, CG-07, CG-10, CG-11, CG-12):

| **Row type** | **When** | **Content** | **`al3Use`** |
|---|---|---|---|
| `GATE_CRITERION` | Criterion test method does not name TEST, SCENARIO_EXERCISE or REPERFORMANCE. | The criterion's evidence and the criterion text; the gate's required classes; effective floor S3 at DESIGN/IMPLEMENTATION depth (AIDCF-010 Part VIII); the gate UNKNOWN ceiling as the unknown effect. | `MANDATORY` |
| `GATE_CRITERION` | Criterion test method names TEST, SCENARIO_EXERCISE or REPERFORMANCE (GC-05-4, GC-05-6, GC-05-7, GC-06-4, GC-06-6, GC-07-3, GC-07-7, GC-10-3, GC-10-4, GC-10-5). | As above; the pilot reviews existing test, commissioning, acceptance or exercise records and performs no test. | `MANDATORY_EXISTING_RECORDS_ONLY` |
| `GATE_CRITERION` | CG-11 and CG-12 criteria. | Satisfied from the assessment team's own records (evidence assessments, manifest, UNKNOWN register); not requested from the host. | `ASSESSMENT_RECORD` |

# 5. Issuing and tracking

1. At SG2 the evidence lead copies the CSV into the controlled repository, adds the pilot prefix and the tracking columns below, and issues it to the host evidence coordinator as the WP-06 request set.
2. Rows are grouped for the host by custodian (electrical, mechanical, controls, compute, storage, network, operations, procurement), not by control.
3. For each received item the evidence lead records evidence ID, source, collector, custodian, classification and integrity reference (AMH-REQ-024), and links the item to every row it answers.
4. Configuration evidence records extraction method, privilege and timestamp; an extract without that context is treated as E1 until corroborated (AIDCF-009 B8).
5. A row that is refused, inaccessible, stale, partial or met by a substitute is recorded as an UNKNOWN Record with type U1–U10 and severity determined by the AIDCF-010 Part IX test (AIDCF-009 B6 step 6). The `unknownEffect` column gives the registry's stated severity for that control; the assessor applies the test to the actual circumstances and records the determining question.
6. `AVAILABILITY_ONLY` rows are closed as EXISTS (with date and holder), DOES_NOT_EXIST or NOT_PROVIDED. They never generate an UNKNOWN Record and never affect a result.

Tracking columns added to the issued copy:

| **Column** | **Values** |
|---|---|
| `custodian` | Host role responsible. |
| `dueDate` | Date required. |
| `receiptStatus` | RECEIVED, PARTIAL, REFUSED, INACCESSIBLE, SUBSTITUTED, NOT_YET (WP-06), or for availability-only rows EXISTS, DOES_NOT_EXIST, NOT_PROVIDED. |
| `evidenceIds` | Evidence Objects linked to the row. |
| `unknownId` | UNKNOWN Record raised, if any. |
| `hostHours` | Host effort to fulfil (PM-02). |
| `receivedDate` | Date received (PM-03 timeliness). |

# 6. Notes for the assessor

- Floors from the profile are never weakened (EVM-REQ-023; AMH-REQ-022). A capability profile may strengthen them.
- For `CLAIM_TYPE_PATTERN` rows the S3 sufficiency target is the pilot's interpretation of AIDCF-008 §31 and §25 (AIDCF-PIL-001 §6.5). Record each case where it changed a result under PM-20.
- The `independence` text on pattern rows is the profile's requirement for p; apply the part that is relevant to the shallower claim type and record what was applied.
- Documentary evidence (E1) alone does not support an IMPLEMENTATION result (AIDCF-009 B7 limit).
- Gate criteria marked `MANDATORY_EXISTING_RECORDS_ONLY` that cannot be met from existing records leave the criterion unmet for lack of evidence: the gate is UNKNOWN with a US4 UNKNOWN Record, not FAIL, unless the records that do exist show the criterion is not met.
